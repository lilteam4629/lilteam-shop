# Main / Cloud payment boundary

Version 1 shares provider configuration and execution, not user balances. Endpoints mount under /internal/api and inherit its required secret and main-site-only guard. /payments/config returns receiver details and readiness without provider secrets. /payments/slip receives multipart image, amount, userId, requestId, creation time and retry state, uses the same verification helper as main account topups, applies the receipt-time policy, and claims the transaction reference before returning success. A durable result cache makes successful retries idempotent.

/payments/truemoney reserves voucher ownership before calling the main configured provider. Cloud ownership uses a rent: user namespace and externalWallet marker. Main wallet credit/reconciliation never handles external claims. Accepted provider amounts are persisted centrally and can be retrieved after a Cloud credit-write interruption. Cloud keeps its own idempotent wallet transactions and recovery loop. /payments/history registers already accepted Cloud voucher history without crediting any main user and reports collisions with main records.

Receipt claims are global, source/request-bound, and durable in the configured store. Main approved historical receipts and voucher wallet transactions are checked. Manual approval needs a transaction reference and must claim it too. Existing storage and deployment remain in use; no database engine migration is needed.

Deploy main first, verify sharedPaymentGatewayVersion:1 in /health, then deploy Cloud. Cloud /health/payment checks the authenticated server connection and readiness without a payment. Integration regression lives in the rental repository scripts/test-shared-payments.js; set MAIN_SHOP_SOURCE to this checkout if repositories are not adjacent. It uses isolated stores and stubbed providers, including simultaneous submissions and interrupted credit recovery. Main receiver, TrueMoney, partner topup, security and local transaction checks also apply.
